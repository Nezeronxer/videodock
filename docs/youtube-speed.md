# Реальные загрузки YouTube и скорость

Продолжение 04.11: [свежий отчёт](stability-2026-11-04.md). Диапазоны уменьшены до 1 МиБ: 4 МиБ принимались video CDN, но отклонялись audio CDN. Полный повтор подтвердил короткий ролик и HD-трейлер; три BBB-проверки всё ещё дают HTTP403 на следующих диапазонах. Большие YouTube-файлы пока не исправлены.

Проверка начата 03.11.2026, продолжена 04.11.2026 на Arch Linux. Rust извлекает ссылки и передаёт данные; FFmpeg получает только локальные файлы. Публичные ролики проверены в отдельных тестовых папках, без пользовательских cookies. Это проверка конкретных samples, не обещание поддержки любого видео YouTube.

## Подтверждённые причины

До исправлений `Me at the zoo` (video433081B + audio309288B) получал metadata за1.268с, передавался18.767с (~39.6KB/s), обработка занимала0.114с. Готовый файл744360B,19.064с,320×240 H.264+AAC.

Контроль на тех же signed streams с одним изменением заголовка:

| Поток | GET без Range | Bounded Range на размер файла |
|---|---:|---:|
| Видео433081B | 9.494с | 0.879с |
| Аудио309288B | 9.437с | 1.519с |

Повтор: видео9.393→0.536с, аудио9.828→0.196с. Раскрытие манифестов0.000с: задержка в HTTP передаче, не в RustyPipe metadata или FFmpeg.

YouTube adapter теперь даёт каждому потоку с известным ненулевым размером собственный `Range: bytes=0-(size-1)`. Unknown/0 не получают диапазона, max-u64 не переполняется. Заголовки авторизации к этому не добавляются; адреса и подписи не меняются. Параллельная передача выбранных дорожек реализована отдельно в core pipeline.

Для большого файла одного bounded Range недостаточно. На том же BBB720p stream через один явный SOCKS proxy диапазоны1/2/4/6MiB возвращали206, а8/12/16/32MiB и весь файл75MB -403. Контрольные64KiB GET для video136/298 и audio140/251 проходили на обоих BBB samples. Размер диапазона воспроизводимо менял206 на403; это не доказательство поломки подписи. Core transfer дорабатывается отдельно для нескольких ограниченных диапазонов с проверкой Content-Range/ETag.

## После bounded Range и параллельных дорожек

| Sample и маршрут | Metadata | Передача | Mux/probe/publish | Проверенный результат |
|---|---:|---:|---:|---|
| zoo240p,direct | 1.102с | 0.175с | 0.079с | 744360B,19.064с,320×240 H.264+AAC |
| zoo240p,direct повтор | 1.790с | 0.259с | 0.081с | тот же размер, длительность и кодеки |
| zoo240p,explicit SOCKS | 0.774с | 0.183с | 0.077с | тот же размер, длительность и кодеки |
| Sintel trailer,explicit SOCKS | 0.781с | 1.764с (~6.85MB/s) | 0.119с | 12073065B,52.234с,1920×818 H.264+Opus |

Sintel имеет киноформат1920×818; потолок1080 в настройках не создаёт отсутствующие чёрные поля. Assert сравнивает выбранную реальную геометрию с ffprobe. Это Full-HD ширина, не1920×1080.

До chunked transfer оба BBB720p samples (`YE7VzlLtp-4`,`aqz-KE-bpKQ`) выдавали403 на большом Range; direct Sintel выдавал503/таймаут, через explicit SOCKS передался полностью. Через другой существующий HTTP egress YouTube отклонял player metadata. Это отдельный ответ сервера, не доказательство поломки CONNECT. Системные VPN/zapret/прокси не менялись. Отказы не считаются успешными скачиваниями.

## Повтор и доказательства

Opt-in harness `crates/core/tests/youtube_downloads.rs`: полные короткий/HD/длинные samples, предел500MiB и180с передачи, проверка audio/video, выбранной геометрии и полной длительности. Диагностические probes без assertions в поставку не оставлены.

Команда: `cargo test -p videodock-core --test youtube_downloads --offline complete_ -- --ignored --nocapture --test-threads=1`, с обычными для проекта `CARGO_BUILD_JOBS=2` и внешним `CARGO_TARGET_DIR`.

Тестовый `VIDEODOCK_TEST_PROXY` одинаково применяется к RustyPipe metadata и reqwest media; значение не выводится. `VIDEODOCK_TEST_OUTPUT_DIR` сохраняет MP4 вместо удаления временной папки. Proxy credentials не следует включать в публичные команды/журналы.

Шесть offline YouTube unit tests прошли, включая bounded Range regression и player-to-Format для video/audio. Артефакты: `~/.local/share/videodock/research/youtube-speed-2026-11-04/`: before/after/controls logs, MP4 в `files/`, независимый `files-proof.json` от ffprobe. Explicit proxy не гарантирует пригодность любого exit IP для YouTube.

Остаётся повторить большие ролики после chunked transfer, раздельно записать direct/proxy. Аккаунты, закрытые/платные видео, все кодеки/регионы и macOS/Windows этим прогоном не проверены.
